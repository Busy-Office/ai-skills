# The interview — the few questions worth asking

Intent belongs to the person, not to the reviewer. Everything a file can
answer, answer from the file. What is left is the interview: **at most
five questions, asked once, in one message**, each with options so it can
be answered in a word.

Ask only questions whose answer changes the draft:

1. **Who** — *"Whose day gets better first: `<role A>` or `<role B>`?"*
   Ask when the sources name no audience, or name three.
2. **The change** — *"After this works, what does that person stop doing?"*
   Ask when every statement is an output. This is the highest-value
   question on the page.
3. **The measure** — *"Which would you accept as proof: `<observable X>`
   or `<observable Y>`?"* Offer candidates drawn from the sources; never
   ask an open "how will you measure success".
4. **The trade** — *"When `<focus A>` and `<focus B>` compete for the next
   month, which one waits?"* This is what produces a real non-goal, and
   the answer usually rewrites the objectives.
5. **The horizon** — *"By when should the measure have moved: 6 weeks, a
   quarter, a year?"*

## Rules

- Draft first, ask second. Bring a draft built from the sources with the
  gaps marked, so the questions are corrections rather than homework.
- Never invent the answer. An unanswered question stays visible in the
  draft as `TO DECIDE — <the question>`; it does not get a plausible
  sentence written over it. A fabricated purpose is worse than a missing
  one, because the loop will obey it.
- Where the repo already answers a question, say so and move on: *"The
  README says the audience is small teams — assuming that unless you say
  otherwise."*
- Do not ask what the code can tell you. Who uses it, what it does, what
  shipped — read it.
- One round. If answers arrive, produce the final draft; if they do not,
  hand over the draft with its `TO DECIDE` lines intact and say which
  ranking decisions are blocked by each.
